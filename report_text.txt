Part I — The Product
1.1  What Stardust Is
Stardust is a physics-based, multi-lens note-taking canvas for the web. It is not a markdown editor. It is not a task manager. It is an interactive cognitive environment where notes exist as physical bodies in space, governed by a physics engine, evaluated by a cognitive worker, and displayed through five distinct analytical lenses called modes.
Each mode — Void, Matrix, Orbital, Prism, and Timeline — represents a different cognitive frame applied to the same underlying note data. Switching modes does not change the notes; it changes the question you are asking of them. Matrix asks: what matters most right now? Orbital asks: what is losing momentum? Prism asks: how do these ideas connect? Timeline asks: what am I actually working on?
The physics engine governs note position, spring forces, drift, and orbital motion. The cognitive worker (a Web Worker running a WorkerBridge) evaluates each note against the active mode's criteria and returns layout targets. The result is a canvas that feels alive — notes drift, orbit, fade, and respond to interaction in ways that a static list never could.
1.2  The Core Differentiators
AI as physics engine: AI determines where notes live in space — not as a writing assistant, but as a layout intelligence layer.
Five cognitive lenses: No other tool offers mode-switching across Eisenhower (Matrix), gravity (Orbital), semantic clustering (Prism), and temporal velocity (Timeline) from one canvas.
Decay mechanics: Notes age and fade based on inactivity. The canvas is a living organism, not a filing cabinet.
Sensory design: Spatial audio, physics-driven animations, and a distinct visual identity make Stardust feel unlike any other productivity tool.
Local-first architecture: All data lives in IndexedDB. No account required. No server. AI features are opt-in.
1.3  Audit History
This report consolidates three successive audits of the Stardust codebase. Each audit built on the previous one.

1.4  The Completion Thesis
Stardust is not a broken product. It is an incomplete product. The architecture is sound — IndexedDB, WorkerBridge, physics engine, mode components, and RichTextEditor are all correctly designed. The failure is wiring. Data does not flow from the engine back to the store. The database is never called. Mode components are not mounted. The persistence layer writes to nothing.
This is a solvable problem. It does not require a rebuild. It requires 25 prompts executed in sequence, each wiring one disconnected system to the next, until the canvas is alive from end to end.

Part III — The AI Note-Taking Reckoning
3.1  The Market in 2026
Every major note-taking tool launched or significantly updated an AI layer between 2023 and 2026. The pattern is almost universal: AI was bolted onto an existing paradigm rather than redesigning it. Notion added AI writing to a database. Obsidian added AI plugins to a file system. Heptabase added AI clustering to a whiteboard. None changed the fundamental UX metaphor.
Stardust's physics-first, multi-lens canvas is the first tool where AI is the engine of the interface — not an add-on. This is the strategic wedge.

3.3  The Five Patterns Defining the Race
AI as writer, not thinker. Most tools help you write better notes. Stardust uses AI to determine where notes live in space, how urgent they are, and how they relate. This is a different cognitive model entirely.
Nobody solved the temporal layer. Notes pile up and go stale. No tool built decay, entropy, and revival as first-class interaction mechanics. Stardust's decay system has no direct equivalent on the market.
The privacy-AI tension is unresolved. Users want smart features but not their deepest thoughts sent to a server. Local-first AI is the winning position for 2027+. WorkerBridge is already architected for this.
Multi-modal capture is becoming table stakes. Voice notes, PDF import, image annotations. Every tool lacking capture parity loses to Apple Notes on mobile.
Second-brain fatigue is real. Users are exhausted from maintaining a system that requires more maintenance than their primary brain. Stardust's physics engine and decay system do the maintenance automatically.

Part VI — Security & System Design Foundations
Every implementation prompt in Part VII carries security requirements, error handling, and system design notes. This section establishes the non-negotiable baseline that all prompts build on.
6.1  Input Sanitization Pipeline
The RichTextEditor produces HTML. That HTML is stored in IndexedDB and rendered in PlanetNote. Without sanitization, a note containing a malicious script tag executes on render — a stored XSS attack.
Rule: DOMPurify must be called at BOTH write time (before IndexedDB) AND render time (before dangerouslySetInnerHTML). Defense in depth.
6.2  Content Security Policy
Add a CSP meta tag to index.html before running any Phase 1 prompt. This prevents inline script injection even if a stored XSS bypasses DOMPurify. CSP must include: default-src 'self', frame-src 'none', object-src 'none'.
6.3  Web Worker Message Validation
All WorkerBridge messages must be validated with Zod schemas before processing. An invalid message silently fails, logs a warning, and does not affect app state. The schema is the contract between the worker thread and the main thread.
6.4  IndexedDB Schema Versioning
Use IDB version numbers and a migration chain. Never destroy data during migration. Old data in new schema gets default values. Increment DB_VERSION with every schema change. Run all migration steps sequentially.
6.5  Error Recovery Architecture

6.6  API Key Security
NEVER hardcode API keys in frontend code, constants.ts, or .env files that are committed.
Route all AI calls through a backend proxy. Proxy holds the key, validates requests, and rate-limits.
User BYOK (bring your own key): encrypt with Web Crypto API. Never store in plaintext in IndexedDB.
Development only: use VITE_ env variables in .env.local only. .env.local must be in .gitignore.
6.7  CRDT Foundation (Future Collaboration)
TipTap (the RichTextEditor) has first-class Y.js CRDT support. Adopting Y.js as the content store for note content now (even without live collaboration) costs minimal complexity but makes real-time collaboration a Phase 5 feature rather than a rewrite. Recommended: use Y.js as the content store from Phase 1 onward.
6.8  Service Worker / Offline Strategy
App shell caching: all static assets cached on install. Second visit = sub-100ms load.
IndexedDB as source of truth: no network required for Void mode, all mode switching, note creation.
AI features degrade gracefully offline: show "AI unavailable offline." Return cached results where possible.
Update notifications: opt-in only via updateNotifier toast. Never auto-reload mid-editing session.

Prompt 0.1 — Security Foundation — DOMPurify, CSP, Zod Worker Validation

Problem Statement
The RichTextEditor produces HTML stored in IndexedDB and rendered in PlanetNote. Without DOMPurify, a note containing a script tag or onerror attribute executes on render — a stored XSS attack. WorkerBridge message payloads are also unvalidated, meaning a corrupted DB read or racing write can send malformed data into the physics engine. This prompt installs the security layer before any wiring begins.

Primary Files: src/utils/sanitize.ts (CREATE) · index.html (add CSP) · src/workers/messageValidator.ts (CREATE) · src/components/PlanetNote.tsx
Secondary Files: src/db/StardustDB.ts (migration versioning) · src/store/noteSlice.ts (sanitize on addNote/updateNote) · package.json

Implementation Steps
Install dependencies: npm install dompurify zod @types/dompurify
Create src/utils/sanitize.ts with sanitizeNoteContent(html: string): string using DOMPurify.sanitize() with ALLOWED_TAGS: [p, strong, em, u, s, h1–h3, ul, ol, li, a, code, pre, blockquote].
In noteSlice.ts addNote() and updateNote() actions: call sanitizeNoteContent(content) before writing to state.
In PlanetNote.tsx: wrap all dangerouslySetInnerHTML with sanitizeNoteContent() wrapper.
Create src/workers/messageValidator.ts with Zod discriminatedUnion schema for all WorkerBridge message types.
In WorkerBridge.ts: wrap all worker.onmessage handlers with validateWorkerResponse(event.data). If null returned: log and ignore.
Add CSP meta tag to index.html: default-src self, script-src self wasm-unsafe-eval, worker-src self blob:, connect-src self [AI endpoint], frame-src none, object-src none.
Update StardustDB.ts upgrade() function to versioned migration pattern with DB_VERSION constant. Set to current version.
Add clampCoord(v: number): number utility (Math.max(-50000, Math.min(50000, v))). Apply in CanvasInputHandler before any coordinate reaches the engine or store.

Implementation Steps

Space+drag: always starts CANVAS_PAN regardless of hit-test result. Check panMode state from uiSlice.
